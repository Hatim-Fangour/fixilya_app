## Why Not Playwright (Browser)?

Playwright was launched first but rejected by CORS when making API calls from `about:blank`. The API is a pure REST backend with no web UI — Playwright's browser fetch is blocked by CORS unless the request originates from the same domain. Switching to a **Node.js HTTP test script** (no browser, no CORS) was the correct tool: direct TCP connections, full header control, no CORS policy. The script creates real Firebase test users via Admin SDK, gets valid ID tokens, runs all tests, and tears down the users.

### Call Architecture Observations

The call service is well-implemented and security-hardened:

1. **Booking authorization gate:** `initiateCall` queries Firestore for a booking with `status in [confirmed, in_progress]` between caller and callee — in both directions. Neither party can call someone they don't have an active booking with. This prevents unsolicited calls.

2. **Server-side token generation:** Agora tokens are never generated client-side. The server generates `callerToken` on initiate and `calleeToken` on accept, separately. A client cannot forge a call session.

3. **Transactional accept:** `acceptCall` uses a Firestore transaction to read-then-update the call document. If two concurrent accept requests arrive, only one succeeds — the second sees `status !== 'ringing'` and gets 409.

4. **Token caching (auth-service agora endpoint):** The `/agora/token` endpoint uses an in-memory `Map` with a 60-second safety buffer before TTL expiry. Same `channelName + uid + role` within the TTL window returns the same cached token — confirmed by test 7.

5. **Rate limiting:** 10 requests/minute on `/calls/initiate` per IP — tested and confirmed.

## All Bugs Found & Fixed During Testing

### Bug 1 — `auth.controller.js`: `auth` variable commented out ❌ FIXED
**File:** `services/auth-service/src/controllers/auth.controller.js:2`
**Problem:** `const { auth } = require(...)` was commented out. The `validateToken` function called `auth.verifyIdToken()` on `undefined`, throwing a TypeError caught as a generic 401.
**Fix applied:** Uncommented the import. **Requires auth-service restart.**

### Bug 2 — `notification-service/app.js`: `dotenv` loaded without explicit path ❌ FIXED
**File:** `services/notification-service/src/app.js:1`
**Problem:** `require('dotenv').config()` with no path loads `.env` from the **current working directory** (cwd), not from the service's own directory. If the service is started from a different folder, Firebase credentials are missing/wrong.
**Fix applied:** Changed to `require('dotenv').config({ path: path.resolve(__dirname, '..', '.env') })`. **Requires notification-service restart.**

### Bug 3 — Booking & notification services: stale Firebase credentials ⚠️ REQUIRES RESTART
**Problem:** Both services were started before the Firebase project was migrated from `fixilyaapp-10ca8` → `fixilyaappbackend`. The Firebase Admin SDK is initialized once at startup and holds credentials in memory. Tokens issued for `fixilyaappbackend` are rejected.
**Fix:** Restart both services. The `.env` files already have the correct credentials.

### Bug 4 — Missing Firestore composite index for notifications ⚠️ RESOLVED (index built automatically)
**Collection:** `notifications`
**Required index:** `userId ASC` + `createdAt DESC`
**Status:** Index was built between the handyman and client test runs. Client test 30 (`GET /notifications`) passed with 200. If the index does not exist on a fresh project, create it manually:
Firebase Console → Firestore → Indexes → Composite → Add index → collection: `notifications`, fields: `userId (Ascending)` + `createdAt (Descending)`.

### Bug 5 — `POST /bookings`: Wrong field name and missing required fields ❌ FIXED
**File:** `test_client.js` (test script, not production code)
**Problem:** Initial booking creation payload used `serviceType` but the endpoint requires `service`. Also missing required fields: `city`, `clientName`, `clientPhone`. Booking service returned 400 validation error.
**Fix applied:** Corrected all field names and added missing fields in `test_client.js`. This is a documentation/contract gap — the booking service's required fields are not all obvious from field names.

### Bug 6 — Missing Firestore composite index for bookings (client list) ⚠️ ACTION REQUIRED
**Collection:** `bookings`
**Required index:** `clientUid ASC` + `createdAt DESC`
**Problem:** `GET /bookings` (client listing) returns `9 FAILED_PRECONDITION: The query requires an index`. Index was queued for building during the test run but not yet active.
**Fix:** Firebase Console → Firestore → Indexes → Composite → Add index → collection: `bookings`, fields: `clientUid (Ascending)` + `createdAt (Descending)`.
Also create: `handymanId (Ascending)` + `createdAt (Descending)` for handyman booking queries.

### Bug 7 — Booking creation blocked by `isAvailable: false` ⚠️ DESIGN NOTE
**Service:** `booking-service`
**Problem:** The booking service checks the handyman's `isAvailable` flag before creating a booking. When test users are created programmatically via Firebase Admin SDK, `isAvailable` defaults to `false`. This causes 400 `"Provider is not currently available"` even for valid test scenarios.
**Fix in tests:** Set `isAvailable: true` in the handyman Firestore document during test setup.
**Production behavior:** Correct — handymen must explicitly toggle availability on. New handymen are unavailable by default until they set their status.

### Bug 8 — Favorites endpoint accepts non-existent handyman IDs ⚠️ DESIGN GAP
**File:** `services/user-service/src/` (favorites route handler)
**Problem:** `POST /users/client/favorites/:handymanId` with a non-existent `handymanId` returns 200 instead of 404. The endpoint appends the ID to the client's favorites array without verifying the handyman exists in Firestore.
**Impact:** Low — clients can accumulate phantom favorites that will never resolve to a real profile.
**Recommended fix:** Add a Firestore lookup (`handymen.doc(handymanId).get()`) before updating favorites. Return 404 if document does not exist.
**Current status:** Not fixed — no code change applied.

### Bug B4 — Dispute & Resolve routes not registered in booking-service ✅ FIXED
**File:** `services/booking-service/src/routes/booking.routes.js`
**Problem:** The booking service's state machine (`booking.service.js`) fully defines the `in_progress → disputed` and `disputed → resolved` transitions with proper role guards (`client` for dispute, `admin` for resolve). However, the HTTP routes `PUT /:id/dispute` and `PUT /:id/resolve` were **not registered** in `booking.routes.js`. All calls to these endpoints returned `404 Route not found`.

**Fix applied (2026-03-09):**
1. **`booking.routes.js`** — Added two new routes:
   ```js
   router.put('/:id/dispute', [param('id').notEmpty(), body('reason').optional().isString().trim(), validate], ctrl.disputeBooking);
   router.put('/:id/resolve', [param('id').notEmpty(), validate], ctrl.resolveBooking);
   ```
2. **`booking.controller.js`** — Added `disputeBooking` and `resolveBooking` controller methods with full audit logging, following the same pattern as `cancelBooking`/`declineBooking`.
3. **`booking.service.js`** — Added thin wrapper methods `disputeBooking()` and `resolveBooking()` that delegate to `updateStatus()`.
4. **`booking.service.js`** — Added `BOOKING_DISPUTED` and `BOOKING_RESOLVED` to the `EVENTS` constant and wired them into the `eventMap` and `notifMap` in `updateStatus()`:
   - `disputed`: notifies the handyman (provider) that a dispute was raised
   - `resolved`: notifies the client that the dispute was resolved by admin
5. **`booking.service.js`** — **Fixed a silent access-control bug**: `TRANSITION_ACTOR.resolved = 'admin'` was defined, but the actor guard only checked for `'provider'` and `'client'` — non-admin users could have triggered the `resolved` transition. Added an explicit `requiredActor === 'admin'` check that throws 403 for non-admin callers.

**Requires booking-service restart.**

### Bug B5 — Review endpoint returns 201 instead of 200 ⚠️ MINOR
**File:** `services/booking-service/src/controllers/booking.controller.js` (review handler)
**Problem:** `POST /bookings/:id/review` returns HTTP 201 Created. Since submitting a review updates an existing booking document rather than creating a new resource, HTTP 200 is more semantically correct. The review IS submitted successfully — this is a status code inconsistency only.
**Recommended fix:** Change `res.status(201).json(...)` to `res.status(200).json(...)` in the review controller.

### Bug B5b — `PUT /notifications/:id/read` with non-existent ID returns 500 ⚠️ MINOR (found in re-test)
**File:** `services/notification-service/src/services/notification.service.js` — `markAsRead()`
**Problem:** When a non-existent notification ID is passed, `notifDoc.exists` is false and a `throw new Error('Notification not found')` is raised, but it propagates as a generic 500 instead of 404. The error is caught by the Express error handler which doesn't map it to 404.
**Recommended fix:** In the controller, catch the "Notification not found" message and return `res.status(404)` explicitly, or add a dedicated `NotFoundError` class that the error handler maps to 404.

### Bug B6 — Admin has no global booking list endpoint ⚠️ DESIGN GAP
**Service:** `booking-service`
**Problem:** `GET /bookings` for an admin-role user uses the `providerId` query path, returning only bookings where the admin is the handyman. There is no admin-specific endpoint to list all bookings across all users.
**Impact:** Admin cannot view system-wide bookings without knowing individual booking IDs.
**Recommended fix:** Add a `GET /bookings/all` admin-only endpoint that queries without user filtering, protected by `requireRole('admin')` middleware.
